## 1. 发现 1（阻断——真实模式主判据）：RealGuiClient 应答解包与 wire 形态不匹配

**评审方探针实锤 wire 序列化**（对 crates/ipc 实际 `serde_json::to_string` 输出）：

| 变体 | wire 实际形态 |
| --- | --- |
| `GuiReply::Items` | `{"Items":[]}`（外部不可辨名，**无 t 字段**） |
| `GuiReply::Ok` | `"Ok"`（**裸字符串**） |
| `GuiReply::Status` | `{"Status":{snapshot}}` |
| `GuiReply::FilePath` | `{"FilePath":"…"}`（桥内拦截 opener 后不外泄） |

而 client.ts 全部按 `r.t === 'Items' / 'Status' / 'Ok'` 解包（types.ts GuiReply 为 **tagged 形态** `{t,…}`）→ **r.t 恒 undefined**。真实模式（`#realIpc`）后果链：List 恒 `[]`、status() 恒 `{running:false,…}` → **EX-10 横幅常驻**、store.refresh 恒清空 items、sendText Ok 判定恒失败。通知方向不受影响（Rust 侧 retag `{t,payload}` 与 types 对齐——恰与应答方向形成**不对称缺陷**）。

**性质**：mock/桩 ≠ 真实实现的同型逃逸**第三次**（E3 → PR-34 §9.2 → 本 PR）——冒烟 8/8 全为 mock 模式（CHECKLIST 自述），真实模式零覆盖。系统性风险点名：凡双实现（mock+real），验收口径必须以真实链路冒烟为准。

**修复建议（对称 retag，一行级方案）**：`svc_request` 返回前仿 notify 的 retag 对称处理 reply——按 types.ts GuiReply 契约键整形：`Ok`（裸串特判）→ `{t:'Ok'}`；`Items` → `{t:'Items', items:[…]}`；`Status` → `{t:'Status', snapshot:{…}}`（FilePath 已被桥内 opener 拦截返回 Ok，不外泄）。此后 client.ts **无需改动**（r.t/r.items/r.snapshot 即匹配），types.ts GuiReply 类型即真实。**修复后必须以 `#realIpc` + 真实 svc 重跑冒烟补真实模式证据**（现 8/8 未能覆盖发现 1）。
