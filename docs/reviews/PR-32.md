## 2. 发现问题

### 发现 1（严重——request changes 直接依据）：PR 描述 4 项功能声明不在本分支
上表 #5③④⑤ 与「重推」共 4 项，描述以「已落地」口吻写入变更说明与「接口扩展与修复（已获批，随本 PR 可见）」段，但代码全部位于 feat/t6-agent。lead 点名核对项「确定性 event_id（event_log 不随重连膨胀）」经查证**不在本 PR**——本分支 event_id 为随机 UUID，重连重推场景（该功能本身也在 t6）下 event_log 膨胀问题在本分支无从谈起。处置二选一：
- **a（推荐）**：修正 PR 描述，把 4 项移入 t6 的 PR 描述（或注明「随 t6 PR 落地」）；本 PR 按 t5 实际内容（准入/查重/广播/清单下发 + net 扩展 #4①②③）重新表述后我改判 approve；
- **b**：由 lead 做分支内容重组（把 t6 的 hub 改动前移进 t5），保持描述不变——工作量与风险更大，不推荐。

### 发现 2（严重——链路一致性风险，须在 t6 合并前解决）：t6 将静默回退 InvalidNickname
t6 分支 rebase 自**无 InvalidNickname 的旧 t5**，而 89578c3（lead 代补）是其后追加的提交。依序 squash merge t5 → t6 时，t6 的 diff 会**删除** hub.rs 的保留名检查与 `reserved_device_name_nicknames_rejected` 测试（已逐行核实 diff），最终 main 上 `HelloErr::InvalidNickname` 成为无使用无测试的死变体，PR #30 检查点（lead 2026-11-15 裁定「t5 开 PR 前补 Join 校验」）被静默回退。**处置**：t6 需 rebase 到 89578c3 之上并确认 diff 不再呈现删除，或人工将检查与测试带回 t6。本项不修复则 t6 PR 必被 request changes。

### 发现 3（一般）：ack 跟踪未实现且无归属
M1 计划 T-05 行为明确「收集 FileAck/事件 ack」；t5/t6 的 hub 均未处理 FileAck（net 会话层正确忽略，角色层无消费），sync_state 停留在 Synced 无确认语义。M1 TC 用例不直接测 ack（5.8 的「24/28 台」属 M2），但 GUI 状态列（FR-T-04「状态」字段）依赖。建议：归属 t7（ipc 状态上报）或明确 M2，需 lead 定夺并记 Deferral。

### 发现 4（轻微）：文本广播在 t5 阶段的语义空档
t5 的 send_text 仅广播 Event（无正文帧），t6 才补正文推送——t5 单独看，agent 无法取得文本正文。这是链路中间态，**若按发现 1-a 修正描述并依序合并则自然闭合**；仅当 t5 需独立交付时才是问题。记录备查。
