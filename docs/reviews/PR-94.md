## 1. 复用 S3 身份链路 ✓（无另起校验层）

`on_event` 的 S3 四重校验（会话存在 / `owner_id==conn.nickname` / `audience==Teacher` / `owner_role==Student`）原样保留；通过后仅登记 `uploads`。`on_file_chunk_stream` 落库时 **owner 取 `conns.get(session_id).nickname`（服务端权威）**，不取事件自带 `owner_id` ✓；`Role::Student` + `Audience::Teacher` 硬编码 ✓——冒名路径结构上不可达。

## 2. 入库时机 ✓ 半成品路径堵死

- `on_event` 仅 `uploads.insert(session_id, ev)`（元数据登记，**不落库**）
- 内容帧到达：`uploads.remove(session_id)` + **`filter(|e| e.item.id == header.item_id)` 对应校验**（不符 → 排空 + 拒）→ 临时文件写入 → 大小/SHA-256 → 通过才 `put_text` / `put_file_from_tmp`
- **断线清理**：`on_disconnect` 移除 uploads 登记（内容帧不会再来的路径）
- 失败路径全清理：临时文件删除 + 排空 chunks（不阻塞发送端）+ `FileAck{sha256_ok:false}`（创建失败/写失败/超限/哈希不符/入库失败 逐一覆盖）
- → 「元数据先落库、内容永不到」被堵死 ✓

## 6. ⚠️ 一般级加固建议（本 PR 唯一实质发现）：100MB 检查在写入循环**之后**

`on_file_chunk_stream` 的 `while let Some(chunk)` 循环内仅累计 `written`，**循环结束才判 `written <= MAX_FILE_SIZE``。恶意/异常客户端可持续发块（net 层单帧 ≤8MB，但总量无上限）→ 先把 `%TEMP%` 写满再被拒。
**建议**：循环内检查 `if written > MAX_FILE_SIZE { 删临时文件 + 排空 + return sha256_ok:false }`（约 6 行，E10 同源但位置应前移）。教室 M2 环境风险中低，但不符合「不信任客户端」原则。
