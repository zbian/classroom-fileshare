## 2. 发现问题

### 发现 1（request changes 依据）：尾随点/空格 + 保留设备名绕过类型拦截（PRD 9.4 类型安全、EX-05；9.4 路径安全「入库前净化」的 Windows 特有语义缺口）

**绕过链（已本地实证）**：

1. `sanitize_file_name("x.exe.")` → 尾随 `.` 不在非法字符集 `<>:"|?*` 与控制字符内 → `Ok("x.exe.")` 放行
2. `is_risky_ext("x.exe.")` → `rsplit_once('.')` 得扩展名 `""` → 不在 RISKY_EXTS → 不拦截（`"x.exe "` 变体得 `"exe "` 同样不拦截）
3. 落盘时 Windows Win32 剥离尾随点/空格——**实测**：创建 `x.exe.` 与 `y.exe `，磁盘上实际文件名为 `x.exe` 与 `y.exe`
4. 后果：学生发送「作业.exe.」/「作业.exe 」可穿透类型拦截，在教师机与同学机落盘为可执行文件，双击即执行——违反 PRD 9.4「默认拦截可执行文件」与 EX-05 的实质要求

**同类缺口**：NTFS 保留设备名（`CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9`，含带扩展形式 `CON.txt`，微软 Win32 文件命名规范）未拒绝——Win10（PRD 9.3 支持平台）上可能映射设备句柄，打开/创建行为异常。

**修复建议（均在 protocol 层，成本低，且 T-3 未合并、现在修最合适）**：

- `sanitize_file_name`：剥路径后 `trim_end(['.', ' '])`；trim 后为空 → `Empty`；trim 改变了名字（即原名带尾随点/空格）→ 拒绝（建议归入 `IllegalChar` 或新增变体，保守而明确）；保留设备名检查（取首个 `.` 前部分，大小写不敏感比对清单）→ 拒绝
- `is_risky_ext`：取扩展前对入参做同样的尾随点/空格规范化（防御纵深）
- 补测试：`x.exe.`、`x.exe `、`x.pptx.`（正常类型带尾点也应拒）、`con`、`con.txt`、`aux.exe`
