## 3. 发现问题

### 发现 1（阻塞——request changes 依据）：#7① 修订声明失实，OpenItem 接口空洞无归属
描述以「接口修订记录（均经 lead 批准）」口径列出 #7①，但 `GuiReply::FilePath` 在分支全部历史中从未存在。后果：GUI 双击打开条目（Session 0 限制下必须由服务返回实体绝对路径）在当前接口下**不可能实现**——OpenItem 只会得到通用 Ok。处置二选一：
- **a（推荐，PR-32 发现 1-a 同款）**：修正描述——#7① 移出本 PR 修订清单，改注「随 T-13/GUI 接线 PR 落地」，同时给 OpenItem 空洞明确归属声明后我改判 approve；
- **b**：本 PR 补实现（一个枚举变体 + handler 契约），但真实路径返回涉及 store `file_body` 与 svc 接线，跨层工作量更大，不推荐。
另记录：测试桩对 OpenItem 落入 catch-all 返回 Ok，未暴露该空洞——修复时建议补一条「OpenItem → FilePath」或「OpenItem → 明确 Err」的断言防回归。

### 发现 2（一般）：版本不匹配拒绝零测试覆盖
PRD 4.5/checklist 要求的握手版本门已实现且文案达标，但 ipc 全部测试（codec 单测 + 2 集成用例）均未触达 version≠1 分支。建议补一条低层回环用例：直写 `Handshake{protocol_version: 999, token: 正确}` → 断言 `HandshakeRejected` 含双版本号且连接关闭。成本约十行，建议随发现 1 修复一并提交。

### 发现 3（轻微，走评论不计入结论）：read_msg 行分帧无长度上限
`read_until(b'\n')` 对未握手连接即可触发：任意本地进程可写入无换行的超长行，BufReader 缓冲无限增长（内存放大）。net 层有 MAX_FRAME_SIZE=8MB 防滥用先例（T-04 checklist 明确），ipc 组 checklist 未列此条故不计入本次结论；建议对齐加行长上限（消息含路径列表，1MB 富余），与发现 2 同文件顺手可修。

### 发现 4（轻微，记录备查）
- token 文档注释「128 bit 随机」与实现不符：两个 uuid simple 拼接 = 64 hex = **256 bit**（实际更强，改注释即可；描述同句一并更正）
- ACL 限权无测试断言（`icacls` 输出可断言，CI windows-latest 可跑；或不补、留握手兜底口径）
- 死连接惰性剔除：断开后须等扇出 send 失败（通道满 64 条）才清出——M1 GUI 重连频率下无碍，记录备查
