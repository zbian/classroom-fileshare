## 1. net 组逐条勾选

### 1.1 帧格式与上限（计划 T-04 安全约定）✓
- `4B 大端长度(含类型字节) + 1B 类型 + payload`：测试 `frame_header_layout_is_len_plus_type` 直接断言字节布局（Ping 帧 5 字节、长度字段=1）
- `MAX_FRAME_SIZE = 8MB`，`len == 0 || len > MAX` 拒绝；测试：超限拒绝、未知类型字节拒绝、截断帧报错、**1MB chunk 编码后低于上限的守护测试**（防调参回退——高质量断言）
- FileChunk 二进制负载（4B id 长度 + id + 8B seq + bytes）避免 JSON ~4 倍膨胀（PRD 9.1 性能考量），decode 有完整边界检查（过短/长度不符/UTF-8）

### 1.2 Hello 三拒绝（PRD 5.1/6.1、EX-02、4.5）✓
`Hello::Join{protocol_version, nickname, role, pin}` 携带协议版本；`HelloErr::{WrongPin, DupNickname, VersionMismatch}` 三码齐全；测试逐一断言（错 PIN、版本不匹配、重名各独立/合并用例）。业务校验逻辑按计划在角色层实现方（net 层提供机制）——正确分层。

### 1.3 分块 + SHA-256 + FileAck（PRD 3.1、EX-07）✓
- FileChunk ≤1MB 二进制帧；FileHeader 携带整体 SHA-256（衔接 store 的 `expected_sha256`——T-3 修订的哈希来源闭环）；FileAck{sha256_ok}
- TCP 全链路回环测试断言 `ack.sha256_ok == true`
- **「逐块校验」的映射说明**（PRD 3.1 原文「逐块校验，整体以 SHA-256 校验完整性」）：计划 T-04 锁定接口的 FileChunk 无逐块哈希字段——逐块完整性由 TCP 校验和 + seq 转发承担，乱序/丢块由整体 SHA-256 兜底（FileAck=false → EX-07 链路）。实现与计划锁定接口一致，映射成立，记录备查（防后续验收误判）。

### 1.4 Beacon 无 PIN 泄露（PRD 3.4 准入、9.6）✓
`Beacon{protocol_version, room, tcp_port, pin_required, host_name}`——**无 PIN 明文、无个人信息**；1s 周期、255.255.255.255 受限广播、bind 独立 socket + set_broadcast；日志仅记 room/addr/port（host_name 不进日志）。

### 1.5 Manifest（PRD 7.5）✓（帧层）
`ManifestReq` / `Manifest(Vec<(id, version, deleted)>)` 帧定义与编解码齐备并纳入往返测试；业务语义（版本清单比对）按分层归角色层——**t5 分支已核实**含 `on_manifest_req` 回调实现（见发现 1）。

### 1.6 真实 TCP 回环测试 ✓
tokio `TcpListener`/`TcpStream` bind `127.0.0.1:0` 真实对连（MockHandler 仅是业务回调桩，传输层零 mock）——checklist「测试用真实 TCP 回环，非 mock」达成。

### 1.7 端口约定（计划 RK-07 落地；PRD 5.1 EX-11）✓
`DISCOVERY_PORT=47820` / `DEFAULT_TCP_PORT=47821` 常量 + 注释明确「冲突时由 host 层自动更换并上报」——EX-11 完整闭环归 T-5（已记为 T-5 PR 检查点）。

## 3. 发现问题

### 发现 1（轻微，描述失实——不改代码，建议修正描述）
PR 描述变更说明称「SessionHandler（on_hello 含 tx 发送通道注册 / on_disconnect / on_manifest_req 默认空方法）——已获批接口扩展 #4①②」，但**本分支代码的 trait 仅三方法**（on_hello 无 tx 参数、无 on_disconnect/on_manifest_req）。已核实这些扩展实际随 **t5 分支**落地（feat/t5-host 对 net 的 diff：完整实现 + on_disconnect 互等避免的注释 + 2 个新测试）——按依赖链切分本身合理，但描述把 t5 内容写进 t4 会误导后续按描述考古。建议：dev 编辑 PR 描述更正该句（或注明「#4①② 随 t5 PR 落地」）；merge 时 lead 知悉即可。**不阻塞合并。**

### 发现 2（观察，验证口径说明）：UDP 端到端发现无自动化
`spawn_discovery` 收包→sink 链路无自动化测试（PR 说明：CI 环境 UDP 广播不稳定；beacon 仅 JSON 往返测试）。理由成立；`manual_addr` 路径（RK-04 备用连接）全覆盖。真实发现时延由 qa 的 TC-01（≤3s 发现）端到端覆盖——建议 qa 执行时保留该口径，无需本 PR 补测。

### 发现 3（观察）：会话层边界防御到位
FileHeader 前 chunk / 无流 chunk / 双 FileHeader 未 End 等边界 warn+丢弃；读写分离独立写任务避免互锁；FileEnd→drop 发送端→触发接收方校验的通道关闭设计干净。Pong/HelloReply 在服务端会话正确忽略。
