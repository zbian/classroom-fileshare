## 1. store 组逐条勾选

### 1.1 覆盖链路 `.part → SHA-256 → 原子替换 → 唯一 .bak → version+1`（PRD 5.7/7.3）✓
`put_file_from_tmp` 实际顺序：净化/拦截 → `copy(tmp→.part)`（同卷保证 rename 原子）→ `sha256_file(.part)` 对照 `expected_sha256` → 旧版 `rename(final→bak)` → `rename(.part→final)` 原子就位 → `version=prev+1` 落索引。
「先 bak 后替换」的两个 rename 是实现「旧版转 bak + 新版原子替换」的唯一正确顺序（后置则旧内容已丢失）；各自原子，PRD 7.3 语义达成。`std::fs::rename` 在 Windows 即 `MoveFileExW(REPLACE_EXISTING)`，files.rs 注释说明与计划「rename 失败退 MoveFileEx」语义等价——成立。占用失败上抛 IO 错误由上层入重试队列（M1 入队+状态、退避 M2）——与 Deferral 口径一致 ✓。

### 1.2 两版后目录恰两文件（TC-06）✓
测试 `file_two_versions_leaves_exactly_one_bak` **字节级断言** `dir_entries == ["作业.docx", "作业.docx.bak"]`、final=V2、bak=V1。**评审探针补验三版**：三版后仍恰两文件、bak 已替换为 V2、version=3——PRD 5.7「只保留最近 1 份备份，新的覆盖会替换旧备份」验证通过（原测试仅两版）。

### 1.3 哈希不符无正式文件（EX-07/9.2）✓
mismatch → 删 .part → `Err(HashMismatch{expected,actual})`；final 不被触碰。测试断言无 final、无 .part 残留。

### 1.4 risky/穿越/保留名拒绝 + 无双清单（PRD 9.4、EX-05；检查点①）✓
- `sanitize_file_name` / `is_risky_ext` / `is_reserved_device_name` 全部复用 protocol；grep 证实 store 源码**仅** `pub use classroom_protocol::is_reserved_device_name`（lib.rs:97）转发，无本地 22 清单、无 `StoreError::ReservedName` 残留——检查点①完全落实。
- 穿越测试三重断言（owner 目录内、仓库根/repo 根无泄漏）；出库侧 `file_body` 再查 rel components（ParentDir/RootDir/Prefix）——双向防御。
- owner 目录名 `safe_component` 拒穿越/非法字符（测试 `bad_owner_id_rejected`）；见发现 2 的保留名补充。

### 1.5 仅写应用数据目录（PRD 9.4 数据位置）✓
布局 `root/repo/<owner>/<净化名>`、文本 `texts/t<scope_hash>.txt`、`root/index.db`；`file_body` 测试断言绝对路径在 repo 内。文本用 scope_hash 命名规避标题非法字符（标题只过 validate_text 不过 sanitize）——正确的设计决策，记录供 T-9/GUI 理解。

### 1.6 schema：作用域键部分唯一索引 + event_log（PRD 3.6/5.7）✓
`ux_share_items_scope ON (owner_id, audience, title) WHERE deleted=0`——与作用域键三元组精确对应；`event_log(event_id PK)`；`PRAGMA user_version` 幂等迁移且拒绝过新版本（PRD 9.5 升级语义）。

### 1.7 apply_remote 幂等（PRD 3.6）✓

## 3. 发现问题

### 发现 1（一般，非代码缺陷、需 lead 指定归属）：崩溃恢复逻辑无归属
PRD 9.2 要求重启后「依据 SQLite 索引与临时文件清理恢复」。两个具体场景：
1. 崩溃残留的 `*.part` 无任何层清理（Store::open 不做，T-5/T-6/T-13 描述亦无）——后果仅磁盘占用，无正确性危害；
2. `rename(final→bak)` 成功后、`rename(.part→final)` 前崩溃：目录有 bak 无 final，索引仍指 final → 条目双击打开失败。**自愈路径已确认**：教师重发同名走覆盖分支（final 不存在则跳过 bak 转换、直接 .part→final）即可修复，课堂场景可接受。
建议：M1 内在服务/agent 启动路径（T-13/T-6）加一步 `清理 root/repo/**/*.part`；bak→final 启动回滚留 M2。请 lead 指定归属 issue（可并入 #14 服务启动项或开新 issue）。

### 发现 2（轻微，转 T-5 检查点）：`safe_component` 未过滤保留设备名
owner_id（昵称）作目录名未查 `is_reserved_device_name`。探针实测 Win11 允许创建 `con` 目录（put 成功）；Win10（PRD 9.3 支持平台）行为可能不同（创建失败→put 报 IO 错，功能受损不失控）。建议 T-5 host 的 Join 昵称校验拒绝保留名昵称（错误提示可复用「请换一个昵称」文案，PRD 8.3）。

### 发现 3（轻微观察）：`upsert_item` 用 `INSERT OR REPLACE`
唯一索引冲突时静默删行——当前所有路径均先 find_scope（含 apply_remote 的显式让位删除），行为安全；但未来若新增绕过 find_scope 的写入点会被静默合并。建议保留现状并留注释，或 T-4/T-5 消费时注意。
